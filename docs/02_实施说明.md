## 二、两个必须知道的修正（相比第一版方案）

### 2.1 金额尺度：不能无脑 ÷10000

第一版方案写"金额是货币型，存储值=元×10000，迁移时 ÷10000"。
**实测结论：这个结论只对"直接解析 .accdb 字节"成立。**

用 Access ODBC 驱动读取时，驱动已经把货币换算成"元"了：

```
SELECT 金额合计 FROM 送气单  →  Decimal('6699.0000')   ✅ 已经是 6699 元
```

所以 ETL 里**不再除 10000**（见 `etl/extract_accdb.py` 的说明）。若按第一版执行，全库金额会缩小一万倍。

验证依据（全库 968 张送气单）：
- 明细 `金额 = 实瓶数量 × 销售单价` → **1417/1417 行全部吻合**
- 主表 `金额合计 = Σ明细金额` → **2,825,470.01 = 2,825,470.01 完全一致**
- 主表 `销量合计 = Σ实瓶数量`（单位=瓶 与 KG 都直接相加，原系统口径，非换算成公斤）

### 2.2 实体与列名用中文

38 表 251 列，如果英文化，要人工映射 251 次，错一个就静默丢字段。
现在 C# 实体、DTO、前端字段名全部沿用中文（`送气单.金额合计`），ETL、SQL、报表、页面字段名完全一致，回归核对 Access 时零翻译成本。C# 与 EF Core 完全支持中文标识符。

```

├─ Database.accdb              原始库，只读基线，任何操作都不写它
├─ db/                         表结构唯一来源（T-SQL 脚本，EF 不建表）
│  ├─ tools/                   生成脚本的脚本（元数据 → DDL / 实体 / 精度配置）
│  ├─ 00_create_database.sql   建库 + 版本表
│  ├─ 01_schema_tables.sql     38 张表（自动生成，勿手改）
│  ├─ 02_constraints_fk.sql    55 个外键（自动生成）
│  ├─ 03_indexes.sql           索引（手写，见第四节）
│  └─ 07_seed.sql              权限资源补齐 + 默认授权 + 系统参数
├─ etl/                        抽数 / 灌库 / 校验
│  ├─ extract_accdb.py         accdb → JSON（ODBC，中文不乱码）
│  ├─ load_sqlserver.py        JSON → SQL Server（单事务，IDENTITY_INSERT）
│  └─ verify_migration.py      行数 / 金额 / 孤儿行 三重校验
├─ backend/                    ASP.NET Core 9 + EF Core 9
│  └─ src/
│     ├─ GasInventory.Domain/Entities/     38 个实体（自动生成）
│     ├─ GasInventory.Infrastructure/      DbContext、通用数据访问、元数据
│     └─ GasInventory.Api/                 控制器：认证/看板/单据/档案/报表/系统
├─ frontend/                   Vue3 + Element Plus（配置驱动页面）
│  └─ src/config/modules.ts    单据与档案的字段配置——加字段只改这里
├─ _setup/                     一键部署（装库 → 初始化 → 迁数 → 打包）
├─ _probe/                     元数据探查与生成器中间产物（交付前可删）
└─ docs/                       方案、实施说明
```

原则：
1. **表结构只有一处**：`db/*.sql`。EF Core 只做映射（`OnModelCreating` 不建表），避免两套结构漂移。
2. **生成的代码不手改**：实体、DDL、外键、精度配置都由 `db/tools/*.py` 从元数据生成，改结构先改源再重生成。
3. **前端不写死字段**：`src/config/modules.ts` 一份配置驱动表格、表单、明细行。

## 四、索引配置（本轮重点）

分层思路：**主键聚集 → 外键 → 业务唯一键 → 复合覆盖 → 筛选**。
命名规则：`PK_表` / `FK_子表_父表_列` / `UX_表_列` / `IX_表_列`。

### 4.1 索引清单（节选）

| 表 | 索引 | 列 | 命中场景 |
|---|---|---|---|
| 送气单 | `IX_送气单_客户日期` | (客户编号, 送气日期) INCLUDE(金额合计,销量合计,单据状态) | 客户对账单、客户历史查询 |
| 送气单 | `IX_送气单_送气日期` | (送气日期) INCLUDE(客户编号,金额合计) | 日报/月报、看板趋势 |
| 送气单 | `UX_送气单_单据号码` | (单据号码) UNIQUE | 按单号定位 + 防重 |
| 送气单 | `IX_送气单_送气员工` | (送气员工编号, 送气日期) INCLUDE(金额合计) | 送瓶员计提 |
| 送气单明细 | `IX_送气单明细_单号规格` | (送气单编号, 钢瓶规格编号) INCLUDE(实瓶数量,空瓶数量,销售单价,金额,提成基数) | 打开单据（覆盖，不回表） |
| 客户 | `UX_客户_客户编码` / `IX_客户_简称` / `IX_客户_电话` | — | 客户定位三件套 |
| 客户 | `IX_客户_业务员` | (业务员编号, 是否有效) | 业务员看自己的客户 |
| 岗位权限 | `UX_岗位权限_组合` | (岗位编号, 资源编号, 权限编号) UNIQUE | 每次请求的权限校验 |
| 登录记录 | `IX_登录记录_员工时间` | (员工编号, 登录时间 DESC) | 登录日志 |
| 计提方案明细 | `UX_计提方案明细_方案规格` | (计提方案编号, 规格编号) | 计提汇总 join |

### 4.2 设计原则

1. 字典表（2~8 行：客户分类、结算方式…）**只留主键**，不建额外索引——全表扫描比走索引还快。
2. 写频繁的明细表索引控制在 **3 个以内**（送气单明细：PK + 单号规格 + 规格）。
3. 复合索引：等值列在前，范围列（日期）在后；报表 SELECT 列进 INCLUDE，避免回表。
4. 低基数状态列用筛选索引，不建全表索引。

### 4.3 怎么验收索引真的生效

```sql
-- 打开执行计划统计
SET STATISTICS IO, TIME ON;

-- 场景 1：某客户某月对账（应命中 IX_送气单_客户日期，逻辑读个位数）
SELECT 单据号码, 送气日期, 金额合计 FROM 送气单
WHERE 客户编号 = 1 AND 送气日期 >= '2026-01-01' AND 送气日期 < '2026-02-01';

-- 场景 2：打开一张单据的明细（应命中覆盖索引，无 Key Lookup）
SELECT * FROM 送气单明细 WHERE 送气单编号 = 2;

-- 场景 3：权限校验（应命中 UX_岗位权限_组合）
SELECT 1 FROM 岗位权限 WHERE 岗位编号 = 1 AND 资源编号 = 1 AND 权限编号 = 1;
```

## 六、怎么跑起来（全在 `_setup/`，2026-10-23 按 v3 重写）

> 第一~五节与第七~九节留作**第二轮（v2，38 表）**的过程记录，环境/端口/账号/跑法**以本节和 `_setup/README.md` 为准**。

前置：SQL Server 2022 Express（实例名 `SQLEXPRESS`、**仅 Windows 认证**、命名管道协议开启，服务 `MSSQL$SQLEXPRESS` 在跑）；
.NET 9 Runtime；建库/灌数据还要 Python 3.10+；只有改前端或重新发布才需要 Node 18+。

| 步 | 双击 | 干什么 | 备注 |
|---|---|---|---|
| 1 | `2-初始化数据库.bat` | 调 `python db\tools\build.py`：先把现库备份到 `db\_backup\`，再按序号执行 `db\v3\` 下 60 个脚本（186 表 / 121 视图 / 128 存储过程 / 26 触发器 / 508 外键 / 428 检查约束 + 种子数据），最后自动跑六套自检（293 项） | 会**删库重建**，脚本里有 Y/N 确认；2~4 分钟 |
| 2 | `3-迁移数据.bat` | `run_stage7_sql.py` 建生成器计划表 → `seed_stage7.py --run --months 12 --customers 200`，用存储过程生成**一整年**业务数据并逐月月结 | 数据是流程跑出来的（单据→过账→库存流水→凭证），不是插数；20~40 分钟 |
| 3 | `4-构建发布.bat` | 前端 `vite build`（`node_modules` 已在就跳过 `npm install`）+ 后端 `dotnet publish -c Release -o publish`，再把 `frontend\dist` 合进 `publish\wwwroot` 并逐字节校验 | 出一个免 Node 的单包；1~2 分钟 |
| 4 | `启动系统.bat` | 起服务并自动开浏览器；**关窗口 = 停止系统** | 每次用都跑它 |

已经建好库的机器只跑第 4 步。

**`启动系统.bat` 的三级回退**，不用先打包也能起：

1. 有 `publish\GasInventory.Api.dll` → 用发布包；
2. 没有但源码编译过（`backend\src\GasInventory.Api\bin\Debug\net9.0\`）→ 直接用编译版；
3. 都没有 → 自动 `dotnet build` 一次再启动。

启动前还会比对 `frontend\dist\index.html` 与将要托管的 `index.html`，不一致就 `robocopy` 重新同步 —— 防的是"改了前端但页面还是旧的"。

### 端口：为什么不是 5080

`appsettings.json` 现在写的是 `http://localhost:10374`。
原因是 5080 落在这台机器 Windows 的**保留端口段**里（`netsh int ipv4 show excludedportrange protocol=tcp` 能看到），
`bind` 直接失败，所以换到不在保留段的 10374。
脚本从 10374 往后扫（10374→10378）挑第一个空闲端口启动，并在窗口里打印真实地址；
若这几个端口全在监听，**不会重复起进程**，直接开浏览器。要指定端口：先 `set GAS_PORT=10380` 再跑脚本。

### 批处理的编码约定（踩过的坑）

`_setup/*.bat` 全部是 **GBK（936）+ CRLF** 存盘，脚本首行 `chcp 936`。
早期用 UTF-8 + `chcp 65001` 时，cmd 会把中文读成乱码，且 LF 换行会让 `if/else` 块解析异常 —— 改这些 bat 时请保持 GBK+CRLF，不要用 VSCode 默认的 UTF-8 另存。

另外两条同样是踩出来的硬规矩：

1. **别用 Git-Bash 的 heredoc / `echo` 生成 bat**：MSYS 会把 `>nul` 改写成 `>/dev/null`，cmd 执行到那一行报"系统找不到指定的路径"，报错和真实原因之间完全看不出关系。要生成 bat 就用文件方式落盘（Python `wb` + `\r\n`）。
2. **别用 `xcopy` 拷到带尾反斜杠的引号目录**：`xcopy … "publish\wwwroot\"` 打印"无效路径 / 复制了 0 个文件"，却返回 errorlevel 0 —— 脚本以为自己成功了，实际发布包里是**上一次的旧前端**（这次就这么中招过一次）。改用 `robocopy src dst /E` + `fc /b` 比对 `index.html` 收尾（`robocopy` 的 exit code 0~7 都算成功，所以校验必须靠 `fc`）。

### 认证方式：Windows 集成认证

本机是 SQL Server 默认安装（`LoginMode=1`，只有 Windows 认证），所以整条链路都不用 sa 密码：

- 连接串（`backend/src/GasInventory.Api/appsettings.json`）：
  `Server=localhost\SQLEXPRESS;Database=GasInventory;Trusted_Connection=True;TrustServerCertificate=True;Encrypt=False;MultipleActiveResultSets=True`
- 建库/灌数/探针用的 Python 脚本走 pyodbc `Trusted_Connection=yes`；TCP 被挡时直接按命名管道连
  `np:\\.\pipe\MSSQL$SQLEXPRESS\sql\query`
- 执行 SQL 以 `db/tools/build.py` 为主入口（按序号跑 `db\v3\` 并能单跑某套自检），**不依赖 sqlcmd**（默认安装不带命令行工具）。
  本节旧版写的 `etl/load_sqlserver.py`、`etl/verify_migration.py`、`db/tools/runsql.py` 是 v2 抽 Access 数据那条路，v3 的数据改由 `seed_stage7.py` 生成，已经不走它们了。

代价是：程序必须以「有该实例权限的 Windows 账号」运行。默认安装会把执行安装的账号加成 sysadmin，所以本机没问题；若要换成服务账号或加域环境，再去开混合认证并改用 sa。

开发模式：`backend` 目录 `dotnet run --project src/GasInventory.Api`，前端 `npm run dev`（5173 端口，`/api` 已代理到 10374）。

### 本轮修掉的 4 个「点开就打不开」级问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 双击 bat 一闪而过 / 服务起不来 | ① 引用了 `Swashbuckle 10.x`，它依赖的 `Microsoft.OpenApi` 版本与运行时冲突，启动即抛 `ReflectionTypeLoadException`；② 旧脚本只认 `publish\`，没打包就找不到 dll | ① 去掉 Swagger（界面已有完整前端，不需要它）；② 启动脚本改为「publish → bin\Debug → 自动编译」三级回退，并把**内容根目录**切到有 `wwwroot` 的那一层（否则首页 404） |
| 看板/列表/部分报表 500 | ① `数据服务` 用 `await using` 把 **DbContext 持有的连接** 释放了，同一请求第二次查询就报 `ConnectionString 未初始化`；② `COUNT(1)` 返回 `int`，代码却 `GetInt64` 强转 | ① 连接不再 Dispose；② 改为 `Convert.ToInt64(GetValue(0))` |
| 所有档案页 403「没有权限：基础资料维护」 | 控制器上挂的 `[资源("基础资料维护")]` 是**资源名称**，而校验比的是 `权限资源.对象名`，库里没有这个对象名，等于全员拒绝 | 改成按表映射到真实对象名（客户→客户明细、员工→员工编辑、钢瓶规格→钢瓶规格…），字典表归到「岗位编辑」 |
| bat 窗口中文全是乱码 | UTF-8 + `chcp 65001` + LF 换行 | 全部转 GBK + CRLF，首行 `chcp 936` |
