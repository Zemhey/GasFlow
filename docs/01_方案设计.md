# 瓶装气进销存系统 — 总体实现方案 v2（现代技术栈重构）

> 2026-10-18 ｜ 状态：已定稿，进入实施
> 决策：Vue3 + Element Plus + ASP.NET Core + EF Core + SQL Server 2022 Express ｜ 本机单机 ｜ 全部数据迁移

---

## 一、现状盘点（实测）

对 `Database.accdb` 完整解析，结论：**这不是空模板，是一个功能已闭环的 Access 系统**，可作为重构的业务蓝本。

| 类别 | 数量 |
|---|---|
| 业务表 | 38 张 / 251 个字段 |
| 表关系（外键） | 60 个 |
| 窗体 | 27 个（含主/子窗体） |
| 报表 | 7 张 |
| VBA 模块 | 8 个 |
| 命名查询 | 19 个 |
| 数据 | 2811 行（32 表有数据，6 表为空） |

核心数据：`送气单` 968 / `送气单明细` 1417 / `岗位权限` 62 / `还瓶单` 40。

### 1.1 功能域

| 域 | 表 | Access 现有窗体 |
|---|---|---|
| 基础档案 | 客户、员工、钢瓶规格、供气商、打气车、客户分类/区域/状态、付款方式、结算方式/账期 | 各 `*编辑` |
| 进气（采购） | 进气单主干/明细 | 进气单编辑 |
| 销售（送气） | 送气单/明细、押金收据 | 送气单 |
| 钢瓶流转 | 借瓶单/明细、还瓶单/明细、每日盘点/明细、入仓单/明细 | **无窗体（缺口）** |
| 计提 | 计提方案/明细、客户提成标准 | 计提方案编辑 + 3 张报表 |
| 对账 | 结算账期/方式、付款方式 | 2 张对账单报表 |
| 系统管理 | 员工、岗位、员工岗位、权限资源/项/矩阵、登录记录、系统参数 | 登录、权限分配 |

> **重构要补的缺口**：借瓶、还瓶、每日盘点、押金收据这 4 组表在 Access 里只有表没有窗体。Web 版必须补上，才算"功能完整"。

### 1.2 两个必须处理的坑

**坑一：金额是 Access 货币型，存储值 = 真实金额 ×10000。**
实测 `销售单价 = 165000` → 实际 16.5 元/kg；`金额合计 = 66990000` → 6699 元（406kg × 16.5 校验通过）。
共 14 个金额列，迁移时统一 ÷10000，落库为 `decimal(19,4)` 的"元"。

**坑二：19 个命名查询依赖 Access 专有函数**（`Last()`、`Nz()`、`IIf()`、`DateSerial()`、`Format()`）。
重构后这些查询必须用 T-SQL 重写为视图或存储过程，不能照搬 SQL。

### 2.1 为什么不用 Access 前端了

原方案是"Access 升迁"，但你选了现代技术重构。取舍如下：

| | Access 升迁 | 现代技术重构（选定） |
|---|---|---|
| 前端复用 | 27 窗体零成本 | 27 窗体全部重做 |
| 界面 | 2010 年代风格 | 现代 Web |
| 部署 | 每台装 Access | 浏览器即可 |
| 扩展 | 受 VBA 限制 | 无限制 |
| 代价 | — | 前期开发量大 |

重构的收益是**长期可维护**，代价是**前两周工作量集中在前端**。数据库层（38 表 + 索引 + 数据）两种方案完全一致，不会返工。

### 3.1 文件管理原则

1. **`Database.accdb` 只读**。任何时候不写它，作为对照与回滚源。
2. **表结构单一来源**：EF Core 实体 + 迁移。索引/视图/存储过程这类 EF 表达不好的，放 `db/*.sql`，在迁移后由脚本执行。
3. **命名映射集中在一处**：C# 实体属性用英文（`DeliveryOrder`、`CustomerId`），通过 `[Table("送气单")]` / `[Column("客户编号")]` 映射到中文列。数据库保真，代码可读。
4. **前端类型由后端 DTO 生成**，不手写两遍（可先手写，后续接 NSwag 自动生成）。
5. **单机部署 = 一个 `publish` 目录**：后端自托管静态文件 + 前端打包产物，双击 `.exe` 即用，不需要 IIS。

## 四、数据库设计

### 4.1 命名策略

**表名、字段名保留中文原名。**

理由：251 个字段、38 张表，英文化需要人工映射，出错概率高；ETL 直接对应，零映射风险；EF Core 的 `[Column]` 标注能完全隔离，前端和 C# 代码里看不到中文标识符。

C# 侧示例：

```csharp
[Table("送气单")]
public class DeliveryOrder
{
    [Key][Column("送气单编号")] public int Id { get; set; }
    [Column("客户编号")]      public int CustomerId { get; set; }
    [Column("送气日期")]      public DateTime DeliveryDate { get; set; }
    [Column("金额合计")]      public decimal TotalAmount { get; set; }
}
```

### 4.2 类型映射

| Access | SQL Server | 说明 |
|---|---|---|
| 自动编号 | `int IDENTITY(1,1)` | 主键 |
| 长整型 | `int` | |
| 短文本(n) | `nvarchar(n)` | 按实测最大长度向上取整 |
| 长文本 | `nvarchar(max)` | |
| **货币** | **`decimal(19,4)`** | **÷10000 转元** |
| 是/否 | `bit` | |
| 日期/时间 | `datetime` | 本项目无 Access 前端了，可用 `datetime2`，但 ETL 从 accdb 读的是 `datetime`，保持一致 |
| 双精度 | `decimal(18,3)` 或 `float` | 公斤数，建议 `decimal(18,3)` 避免浮点误差 |

> 公斤数改用 `decimal` 而非 `float`：过磅重量、气重参与金额计算，浮点会累积误差。

### 4.3 金额列清单（14 个，迁移时 ÷10000）

`钢瓶规格.钢瓶单价/押金单价`、`还瓶单明细.钢瓶单价`、`计提方案明细.提成金额`、`借瓶单明细.押金单价`、`进气单明细.单瓶合算价格`、`进气单主干.金额`、`客户提成标准.提成基数`、`送气单.金额合计`、`送气单明细.销售单价/提成基数/金额`、`押金收据.押金单价/收款金额`。

### 4.4 迁移校验（三重，全绿才算完成）

1. **行数**：38 表逐表比对。
2. **金额**：14 个列 `SUM()` 比对，源 ×0.0001 vs 目标，误差 0。
3. **孤儿行**：60 个外键逐条检查子表孤立记录，预期 0。

## 五、索引设计

### 5.1 分层

| 层 | 索引类型 | 目的 |
|---|---|---|
| L1 | 主键聚集 | 唯一标识 |
| L2 | 全部外键列非聚集 | JOIN、子表按父表查 |
| L3 | 业务唯一（单据号码、客户编码、工号、规格编码） | 快速定位 + 防重 |
| L4 | 复合 + INCLUDE 覆盖 | 报表、对账、计提 |
| L5 | 筛选索引（低基数状态列） | 未完成单据 |

命名：`PK_表` / `FK_子表_父表` / `UX_表_列` / `IX_表_列`。

### 5.2 核心表索引

**送气单**（968 行 → 目标年 10 万）
```sql
PK_送气单            (送气单编号)                        CLUSTERED
UX_送气单_单据号码    (单据号码)                          UNIQUE
IX_送气单_客户日期    (客户编号, 送气日期)  INCLUDE(金额合计, 销量合计, 单据状态)
IX_送气单_送气日期    (送气日期)            INCLUDE(客户编号, 金额合计)
IX_送气单_送气员工    (送气员工编号, 送气日期) INCLUDE(金额合计)
IX_送气单_计提方案    (计提方案编号, 送气日期) INCLUDE(金额合计)
IX_送气单_付款方式    (付款方式编号, 送气日期)
```

**送气单明细**（1417 行，写入最频繁，索引控制在 3 个）
```sql
PK_送气单明细          (送气明细编号)                     CLUSTERED
IX_送气单明细_单号规格  (送气单编号, 钢瓶规格编号)
        INCLUDE(实瓶数量, 空瓶数量, 销售单价, 金额, 提成基数)
IX_送气单明细_规格      (钢瓶规格编号) INCLUDE(实瓶数量, 空瓶数量)
```

**客户**（12 行，档案类，重在"定位"）
```sql
UX_客户_客户编码    (客户编码) UNIQUE
IX_客户_简称        (客户简称)
IX_客户_电话        (联系电话)
IX_客户_业务员      (业务员编号, 是否有效) INCLUDE(客户简称, 客户全称)
```

**钢瓶流转**
```sql
IX_借瓶单_客户日期  (客户编号, 借瓶日期) INCLUDE(应还日期)
IX_还瓶单_客户日期  (客户编号, 还瓶日期)
IX_借瓶单明细_单号  (借瓶单编号, 规格编号)
IX_还瓶单明细_单号  (还瓶单编号, 规格编号)
```

**权限（每次请求都查，最热）**
```sql
UX_岗位权限_岗位资源权限  (岗位编号, 资源编号, 权限编号) UNIQUE
IX_员工岗位_员工          (员工编号, 是否主岗位)
UX_员工_工号              (工号) UNIQUE
IX_登录记录_员工时间      (员工编号, 登录时间 DESC)
```

### 5.3 设计原则

1. 字典表（2-8 行）只留主键，不建额外索引。
2. 复合索引：等值列在前，范围列（日期）在后。
3. 报表查询的 SELECT 列尽量进 INCLUDE，避免回表。
4. 低基数列用筛选索引，不建全表索引。
5. 交付时附"索引—查询"对照表 + 5 条典型查询的执行计划与逻辑读对比。

### 6.3 单据通用模式

进/销/借/还/盘点/入仓六类单据结构相同，抽象为统一模式：

- 主表：单号、日期、往来单位、经办人、金额合计、状态
- 明细表：规格、实瓶、空瓶、单价、金额
- 单号生成：存储过程按 `前缀 + yyyyMMdd + 序号` 生成，事务内保证唯一
- 保存策略：整单提交（主表 + 明细数组一次性提交），服务端事务

这套模式做一次，六类单据复用。

## 八、风险清单

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| 1 | 金额未 ÷10000 | 全库金额放大 1 万倍 | ETL 显式缩放 + SUM 校验 |
| 2 | 单号并发重复 | 单据重号 | 存储过程 + 唯一索引 + 事务 |
| 3 | 明细表删除后主表金额不同步 | 账实不符 | 服务端统一重算金额合计 |
| 4 | 权限粒度粗 | 越权操作 | 后端过滤器 + 前端菜单双向控制 |
| 5 | 报表口径与原系统不一致 | 对账差异 | 用 Access 现有数据做基准比对 |
| 6 | 借/还/盘点无原窗体可参照 | 业务规则不明 | 按表字段反推，交付前与你确认 |
| 7 | 中文列名在 EF 迁移中的默认值 | 建表失败 | 全部用 Fluent API 显式配置 |
| 8 | 浏览器打印分页 | 对账单断行 | 固定表格宽度 + `page-break` 控制 |
